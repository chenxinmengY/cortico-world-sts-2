# 07 · 架构

给要改代码、或者想把这套做法搬到别的游戏上的人看。

---

## 一句话

> 桥把游戏变成 JSON，`protocol.ts` 把它变成**带编号的局面**，`render.ts` 把它压成几百字，
> `world.ts` 管编号什么时候作废、什么时候停手、什么时候叫醒模型。

```
游戏 ──mod──▶ HTTP/SSE (127.0.0.1:18080)
                  │
             bridge.ts        只负责传输：快照缓存、重连、断线后轮询兜底
                  │ 原始 JSON
           protocol.ts        宽容归一化 → NormSnapshot；动作 → 编号；回档检测
                  │ 结构化快照
            render.ts         分区渲染 + 增量：只报变化段
                  │ 几百字文本
             world.ts         编号仲裁、停手、空动作宽限、事件推送、求解器接管
                  │ 工具/事件
               宿主（Cortico）
```

一层只干一件事。改代码前先判断落在哪层（见 [CONTRIBUTING](../CONTRIBUTING.md)）。

---

## 六个不变量

破坏任何一条，都会在真机上炸。

### 1. `start()` 永不 reject

宿主的"World 启动失败"是进程级致命错误。所以外部依赖一律**离线可启动 + 后台重连**：
游戏没开，插件照常亮红灯笼，5 秒重试一次，不影响宿主启动。

### 2. 动作编号只在对应状态码下有效

```ts
stateRef = sha256(`${sessionId}:${revision}`).slice(0, 12)
```

`revision` 是**语义指纹**——内容变了或 `state_version` 变了才变。局面一变，旧码立刻作废，模型必须拿新码重来。

这条同时解决三个问题：并发（她拿旧码动手会被拒）、打断（你插手不会和她打架）、回档（旧码自动失效）。

### 3. 回传给桥的字段名是固定的

| 动作 | 指令体 |
|---|---|
| `play_card` | `{ action, card_index, target_index? }` |
| 其余带编号的动作 | `{ action, option_index }` |

**没有 `index` 这个字段**——写了桥会回 `invalid_request`。这是这套桥最容易踩的坑，
所以 `INDEX_ACTIONS` 里逐条映射编号空间，而不是猜。

### 4. 不给退出类动作编号

```ts
const EXCLUDED = new Set(['save_and_quit', 'abandon_run']);
```

她不该顺手把你的局退掉。这是设计约束，不是遗漏。

### 5. 桥的响应外面永远包一层

```jsonc
{ "ok": true, "request_id": "…", "data": { … } }
```

错误在 `error: { code, message }`，**不在 `data` 里**。别在 `data` 里找 error。

### 6. SSE 事件可能早于订阅到达

`bridge.watch()` 不得清空已缓存的 `snapshot`。曾经清过一次，导致启动首帧被吞、她第一回合不动。

## 为什么只报 diff

每推一次局面 = 一次模型调用，而每次调用都要把历史重发一遍。成本是 O(n²)，不是 O(n)：

| 步数 | 该次输入 | 累计 |
|---|---|---|
| 1 | ~2k | 2k |
| 50 | ~26k | ~700k |
| 200 | ~101k | ~10.3M |

所以设计上做三件事：

1. **局面只报变化段**（`HP 68→61 | E1 28→16`），不重抄静态身份；
2. **状态码替代"再读一遍"**——回执自带局面和编号，默认不需要 `sts2_observe`；
3. **求解器接管时整场不叫醒模型**，一场战斗从 N 次调用压到 1 条摘要。

推导过程和实测数据在 [dev/token-cost-notes.md](dev/token-cost-notes.md)。

### diff 的失效模式：世界模型漂移

纯 diff 有个坑：某步敌人意图从"攻击"变成"蓄力"而 diff 没体现，模型会一直以为它还在打你。

约束：

1. **diff 必须覆盖意图与机制变化**，不只是数值（`|!intent atk12→buff|`）；
2. **每 5 步做一次全量对齐**（短版），漂移窗口不超过 5 步；
3. 实在对不上，发 `sts-2.drift` 让她以当前为准。

## 回档怎么判

三条证据，从硬到软：

| 证据 | 来源 | 判定 |
|---|---|---|
| `num_reloads` 增加 | 存档 `current_run.save` | **读档** |
| `rng.seed` 变了 | 同上 | **换局** |
| `act` / `floor` / 已走节点数**倒退** | 局面 | **回档** |
| 两处以上对不上（但不构成上述） | 局面 | **漂移**（`drift`） |

读不到存档时，全部退回内存判定——功能不受影响，只是少了最硬的那条证据。

**篝火回满血不再被误判成读档**：0.1.6 之前把"血突然满了"当证据，结果休息一次就误报。

## 什么时候停手

四道闸，从软到硬：

| 闸 | 触发 | 行为 |
|---|---|---|
| 空动作宽限 | 桥暂时没给动作（动画、敌方回合） | 等 `combatGraceMs` / `blockedGraceMs`，不判卡住 |
| 连续被拒 | 同一操作被拒 `maxRejectsBeforeStop` 次 | 停手 + 面板说一句 |
| 没动静 | 游戏在等、她不动 `idleNudgeMs` | 先提醒一次，再停 |
| 求解器算不动 | 一次搜索超时 | 冷却 60s 起，指数退避，冷却期内零请求 |

原则：**宁可停住等人，也不瞎猜或硬点。**

## 求解器的两种用法

| 模式 | 开关 | 她在做什么 |
|---|---|---|
| 注记 | `solver`（默认开） | 把"下一步 → 编号"贴一行到局面尾部，**不执行** |
| 接管 | `solverAutoplay`（默认关） | 战斗里由求解器一步步打，整场不叫醒模型 |

接管的交回条件：算不出、编号对不上、血低于阈值、结束回合会死、步数到上限、战斗结束。

两者是独立开关——关掉注记也能接管。

**为什么这么设计**：模型擅长"这一层该走哪条路、这张牌要不要拿"，求解器擅长"这一回合怎么出牌"。
让它俩各干各的，比让模型硬算伤害划算得多。

## 搬到别的游戏

这套骨架和《杀戮尖塔 2》没有强绑定，可复用的部分：

| 可复用 | 需要重写 |
|---|---|
| 状态码绑编号（仲裁/并发/回档一刀切） | `protocol.ts` 的字段映射 |
| 只报 diff + 定期全量对齐 | `render.ts` 的分区规则 |
| 空动作宽限、连续被拒停手 | 各游戏"什么叫卡住" |
| 求解器注记与接管的双开关 | 求解器接口 |
| 闲话直连气泡 | 台词池 |

对照 [cortico-world-sts-1](https://github.com/Phantivia/cortico-world-sts-1)：塔 1 用 Java sidecar，
塔 2 用 HTTP/SSE，桥完全不同但上表这五件事是一样的。
