# LLM Agent 打 STS2：Token 成本优化方案与注意事项

> 自包含简报，可直接贴进其他对话。前提：一个 LLM agent 通过逐步循环玩 Slay the Spire 2，每步把游戏状态渲染成文本发给模型，模型回一个动作。

---

## 0. 现状实测数据

| 内容 | 字数 |
|---|---|
| 环境提示词（每次请求都带） | 1106 |
| 战斗快照（简版 / 全量） | 361 / 596 |
| 选牌屏（8 张） | 420 / 601 |
| 地图 / 奖励 | 213 / 200 |
| 动作回执 | 62 + 变化段 |

单步新增约 600–700 字（≈400–600 token）：状态推送 300+、工具调用 20、回执 300。

**结论：解说不是主要成本，动作循环本身才是。**

---

## 1. 成本模型：这是 O(n²)，不是 O(n)

每次请求都要把此前全部历史重发一遍。按起点约 1500 token、每步 +500 估算：

| 步数 | 该次请求输入 | 累计输入 |
|---|---|---|
| 1 | ~2k | 2k |
| 50 | ~26k | ~700k |
| 200 | ~101k | **~10.3M** |

累计 ≈ 起点×n + 增量×n²/2。

**增量只决定系数，平方才决定量级。**
所以"把单步 600 压到 300"最多省 2 倍；动历史结构能省 1–2 个数量级。优化优先级必须按这个排。

---

## 2. 先测量，别先动手

记录三个字段：`step` / `input_tokens` / `cached_tokens`，把 input 对 step 画散点：

| 现象 | 诊断 | 处理 |
|---|---|---|
| 线性上扬 | 历史全量重发 | 走第 3 节 |
| 基本水平 | 已裁剪过，问题在步数 | 走第 5 节 |
| cached_tokens 恒为 0 | 前缀缓存完全失效 | 先修缓存，白捡 5–10 倍 |

静态段通常占输入一半以上，缓存失效是最容易被忽略的大头。

---

## 3. 层一：把历史从上下文里删掉（1–2 个数量级）

### 核心认知

游戏 agent 和聊天 agent 的本质区别：**状态是马尔可夫的**。当前 HP、手牌、能量、敌人意图、牌组、遗物、地图位置，已经包含做决策所需的全部信息。历史唯一不可替代的产物是**长期计划**，而计划 200 字就能写完。

### 结论：不要摘要历史，要重建状态

- **摘要是有损的**：丢信息 → 重复探索 → 步数上涨，反而更贵；
- **重建是无损的**：游戏状态本身就是完备的。

### 请求模板

```python
def build_request(run, state, recent):
    return [
        # 1. 静态段：一字不动，永远在最前 → 前缀缓存命中
        {"role": "system", "content": STATIC_PREFIX},
        # 2. 战略备忘录：只在选牌/选路/Boss 前更新，≤300 token
        {"role": "user", "content": run.plan_memo},
        # 3. 当前状态：固定 schema，≤180 token
        {"role": "user", "content": render_state(state)},
        # 4. 最近 k 步 diff 回执，k=2~3，每条 ≤60 token
        {"role": "user", "content": render_recent(recent, k=3)},
    ]
```

### 三条硬规则

1. **assistant 历史一条都不留。** 里面是解说和自我推理，对下一步决策零信息量。确实需要让模型看到自己干了什么，就用 `actions_log` 的紧凑编码拼进 user 段（`t3: Strike→E1`），别原样塞 assistant 消息。
2. **解说走旁路。** 解说本身 100 token/步很便宜，但它一旦进了 messages，在第 n 步会被重发 n 次——200 步累计约 2M token。它只在 UI 日志/推流里出现，永不进上下文。省下的钱比"少说两句"多 20 倍。
3. **战略备忘录只在真实决策点更新**（选牌、走地图、商店、事件、Boss 前），不在每个战斗回合更新。内容：牌组构成、HP 曲线关键点、关键遗物、地图进度、已知威胁、当前 build 目标。

## 4. 层二：砍单步体积（2–4 倍）

### 4.1 快照 596 → ~180

散文版的问题是它把**静态身份**和**动态数值**混在一起，每步都重抄一遍静态部分。拆开：

| 类别 | 例子 | 变化频率 |
|---|---|---|
| 静态：身份、机制、打法 | "腐化的哨兵""它在积蓄力量""受击叠力量" | 一场战斗内不变 |
| 动态：数值、意图、手牌 | 40/40、atk12、能量 3 | 每步都变 |

```text
坏：你面前是一个腐化的哨兵，它有40点生命值，正在积蓄力量准备攻击...
好：F1 corrupt_sentinel t3 HP18/40 blk0 str2 |!intent atk18| ; P hp68/80 b0 en3 |hand strike strike defend bash| d5 x3
```

596 中文字 ≈ 400–600 token；180 字符字段式 ≈ 70 token。约 5–6 倍，且决策输入一项没少。

### 4.2 身份是"指针"，策略挂在指针上

`corrupt_sentinel` 不是描述，是**索引**。打法存在别处，只付一次钱。三个挂载位：

**A. bestiary 进静态前缀（推荐）**

```text
# bestiary (act1)
corrupt_sentinel 40hp | t1 atk12, t2 str+2, t3 atk18 | 受击反伤2 | 应对: t1-t2 铺格挡, t3 前爆发
louse 12hp x2 | t1 atk6, t2 curl(+blk8) | 应对: 先杀一只降损耗
```

这段永不改动，被前缀缓存命中。整局按 10% 价格计费一次，之后每步几乎免费。策略知识从"每步 400 token"变成"整局一次 30 token"。

**B. 首次相遇注入**：bestiary 太大塞不进前缀时用。某个怪第一次出现，注入 profile 一次，打 `seen` 标记，后续只带 ID。A 的懒加载版。

**C. 工具拉取**：`info(F1)`，遇到没见过的怪才调一次。冷门怪零常驻成本。

### 4.3 回执 300 → ~60（只给 diff）

```text
HP 68→61 E3→1 | F1 40→28 blk0 | hand 4 | pile d5 x3 | stance neutral
```

### 4.4 环境提示词 1106

拆成"永不改的规则段"和"每步可能变的段"，规则段钉在最前。别每步重新生成——重新生成哪怕只改一个字，前缀缓存全废。

### 4.5 全量状态改 pull 不 push

默认给简版，模型显式要 `state(full)` 才给全量版。现在两档都在推，等于永远付贵的那个。

## 5. 层三：砍步数（10–50 倍，收益最大）

唯一能改系数本身的招：

1. **确定性循环外包。** 战斗内出牌顺序交给脚本启发式（贪心 + 格挡阈值），LLM 只在真实决策点介入：选牌 / 选路 / 商店 / 事件 / Boss 规划 / 异常（HP 低于阈值、没见过的精英）。一局 200 步里通常 150 步是"这张攻击牌打哪个敌人"，信息量极低，交给代码零成本。
2. **一次调用多动作。** 整回合（出 3 张 + end turn）作为单个动作提交，带执行回执，失败再回退。步数直接 /3。
3. **两级模型。** 常规回合走小模型/本地模型，战略节点走大模型。回合决策和选牌决策难度差两个量级。
4. **状态哈希缓存。** 同一个 `(deck, hand, energy, enemy state)` 重复出现直接命中决策缓存，roguelike 里这种重复非常多。

## 7. 注意事项（坑清单）

### 7.1 别做历史摘要，做状态重建

摘要本身花 token，且有损，在游戏场景里是负收益。要的是 `render_state(state)`，不是 `summarize(history)`。

### 7.2 前缀缓存的三个破坏点

- 静态段里塞了时间戳、随机 ID、变动的计数器；
- 动态内容被插到静态段前面；
- 每步重建 messages 数组且顺序抖动。

任何一条命中，缓存 100% miss。

### 7.3 diff 的失效模式：世界模型漂移

纯 diff 有个坑：如果某步敌人意图从攻击变成蓄力而 diff 里没体现，模型会一直以为它还在打你，之后每一步都错。

两条约束：

1. **diff 必须覆盖意图和机制状态的变更，不只是数值。** 用 `!` 显式标记：`|!intent atk12→buff|`。
2. **每 5 步做一次全量对齐**（短版全量，约 120 token），其余步用 diff。漂移窗口不超过 5 步，成本只增 20%。

### 7.4 压缩的真实风险是压掉决策字段，不是丢风味

判据：把"这一步该打谁、打什么、留不留费"列出来，逐个问"做这个决策需要看到什么"，能回答的字段必须全在 schema 里。

STS2 战斗不可省的字段：

```text
P: hp/maxhp, block, energy, hand(每张: 名+费+是否升级), draw/discard/exhaust 数,
   stance/orbs/遗物触发
E: id, hp/maxhp, block, intent(类型+数值+段数 atk12x2), buff/debuff(名+层数),
   turn, 蓄力/阶段状态
```

**intent 必须带类型和段数**，不能只有数值——`atk12` 和 `atk12x2` 是完全不同的应对（12 点格挡 vs 24 点格挡）。这是最容易压丢的一项。

### 7.5 风格问题补在 system prompt，不补在快照

字段化后输出会变干。这是风格不是能力，两条准则就够：

```text
- 输出前用一句话说出这回合的核心判断（≤20字），再给动作 JSON。
- 遇到精英/Boss 时用 3 行说明打法意图。
```

一次性写死、进缓存、不进每步快照。成本比原来低两个数量级，语气还在。

### 7.6 A/B 验证，别靠直觉

同一个种子跑 10 局，散文版 vs 字段版，比胜率、平均步数、平均受伤。

- 字段版胜率掉 → **schema 漏字段**，去补字段，不要回退散文；
- 胜率持平或更高 → 散文那部分纯属噪音。

### 7.7 别把全量彻底关掉

改 pull 之后保留 `state(full)` 和 `info(enemy)` 两个逃生口。模型主动要才给，不能完全没有。

### 7.8 两级模型注意决策一致性

小模型负责常规回合时，战略备忘录必须是它的输入；否则小模型会做出和大模型 plan 冲突的短线操作。

## 8. 实施顺序

| 顺序 | 动作 | 工作量 | 收益 |
|---|---|---|---|
| 1 | 查 cached_tokens，修前缀缓存 | 半小时 | 5–10× |
| 2 | assistant 历史不上传 + 解说旁路 | 1 小时 | 3–5× |
| 3 | 回执改 diff、快照改字段 | 2 小时 | 2–3× |
| 4 | 战略备忘录替代长历史 | 半天 | 收敛到 O(n) |
| 5 | 战斗循环脚本化 + 回合批处理 | 1–2 天 | 3–5×，且变快 |
| 6 | 两级模型 | 半天 | 3–5× |

1–3 半天拿下大头，不改变 agent 行为质量；5 才是治本，但要写战斗策略，属于产品决策。

---

## 9. 成功判据

**账单上 input_tokens 对 step 的散点是水平线，不是斜线。**

一句话总结：**身份和打法要留，但留在"进场时/常驻"这一层；每步只推"这一步变了什么"。**
